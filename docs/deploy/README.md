# Deploying

gostore ships two Terraform targets, each with a step-by-step guide:

| Environment | Where | Guide |
|---|---|---|
| Staging | A VM on a Proxmox VE node | [Deploying to Proxmox](proxmox.md) |
| Production | A Vultr instance | Not written yet — until then, [`infra/terraform/vultr`](../../infra/terraform/vultr/README.md) |

Both run the same stack — the app, Postgres, and an ingress container (Caddy, or a
Cloudflare Tunnel) under Docker Compose on one Ubuntu box — from a shared module. What
each piece of Terraform creates, and why it is shaped that way, lives next to it in
[`infra/terraform`](../../infra/terraform/README.md); these guides are the how.

## Where each value goes

A deploy has **no `.env` for you to edit**. Your local `.env` is only for development,
and the one on the server is generated by Terraform. Every value belongs in exactly one
of three places:

| What | Where | Examples |
|---|---|---|
| **Configuration** | `terraform.tfvars` in the target's directory — local and gitignored | domain, image tag, email addresses, bucket names, a merchant id, an access key id |
| **Terraform's own credentials** | `pass`, exported into the shell that runs Terraform | the Proxmox API token, `VULTR_API_KEY`, `CLOUDFLARE_API_TOKEN` |
| **The store's secrets** | `pass`, as `gostore/<env>/<name>`, pushed to the box by `make secrets` | the Postgres password, the setup token, the PayFast key, the mail and storage passwords |

The line between the first two rows and the third is the important one. Terraform never
sees the store's secrets: it decides *which* secrets an environment needs and nothing
more, so none of them is in its state or in the cloud-init payload a provider keeps. See
[Where configuration and secrets live](../configuration.md#where-configuration-and-secrets-live)
for why.

## The shape of every deploy

1. **Publish an image** — `make publish` from a tagged release; see below.
2. **`terraform apply`** in the target's directory. This provisions the box and leaves
   it idle: the stack cannot start until its secrets exist.
3. **`make secrets ENV=staging`** (or `prod`) from the repo root. It waits for the box
   to finish provisioning, checks that every secret it needs is in `pass` — listing any
   that are missing and pushing nothing — writes them to the box over SSH, and starts
   the stack.
4. **Claim the first admin account** at `/admin/setup` with
   `pass show gostore/<env>/setup_token`.

## Publishing an image

The image is built on a workstation and pushed to GHCR by hand — `make publish`,
usually from a tagged release (`git tag v1.2.3 && git push --tags`). There is no
CI workflow doing this on push; see the Makefile's `publish` target for what it
refuses to do (a dirty tree, an untagged commit) and why.

GHCR makes a newly pushed package private. Set it public in the package's settings
after the first publish, or the server cannot pull it without a token.

## Running it anywhere else

The binary is static and the image is distroless, so it runs anywhere a container does.
Four things are all that separate "runs on a managed platform" from "runs on a VM behind
a reverse proxy", and the server does all four: it reads `PORT` from the environment,
takes a single `DATABASE_URL`, logs JSON to stdout, and serves `GET /healthz`.

Migrations run on boot, before the server accepts traffic, guarded by a Postgres advisory
lock so several instances starting at once cannot race. Where you would rather migrate as
its own deploy step, run the same image with `-migrate` first and start the server after
it exits; `-migrate-status` prints what has been applied.

`-migrate` and `-migrate-status` read `DATABASE_URL` and nothing else. A schema change has
no payment gateway and no session, so a migration job — a CI step, an init container, a
release command — should not have to be trusted with the live merchant key and the session
secret in order to run an `ALTER TABLE`. Give that step the database URL alone.

The cost of that is real and worth knowing: a deployment whose payment or admin config is
broken no longer finds out when migrations run, but when the server starts, with the schema
already moved. `-check-config` is that check made deliberate — it validates the whole
environment, touches nothing, and exits. Run it *before* `-migrate` in a deploy and a
missing `PAYFAST_MERCHANT_KEY` fails while the database is still untouched:

```sh
gostore -check-config && gostore -migrate && exec gostore
```

Every credential can also arrive as a file, `KEY_FILE`, which is how the Terraform
targets supply them — see [Configuration](../configuration.md).
